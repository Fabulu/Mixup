## 1. WHAT PORTED (the core PLAY, per plan 130 section 3 / Wave 132)

1. **`games/ddpdoj/src/web/replay.js`** (extended) -- the PLAYBACK verifier.
   - `decodePortinWords(obj)` -- u16be portin bytes -> `Uint16Array`, mirroring
     `replay.mjs:179 decodePortin`.
   - `armPlayback(game, obj)` -- a verifier that MIRRORS `verifyReplay`
     (replay.mjs:104) but runs on the LIVE `game` and hashes via the browser
     module's ACCUMULATE-then-`sha256Hex` path (same path W131's recorder uses,
     same path the cross-check proved byte-identical to Node incremental).
     `feed()` is called once per logic frame AFTER `g.step()` (the state the step
     produced); period boundaries are recorded as char offsets into the growing
     feed; `check()` (async) hashes each newly-closed 250-frame window FRESH and
     records the first divergence as `{ index, from, to, got, want }` (the
     `replay.mjs:151` shape); `finalize()` (async) closes the trailing partial,
     hashes the cumulative, and returns the verdict
     `{ green, compared, cumulative, cumulativeMatch, cumulativeWant,
     divergentPeriod, periodCount }` -- the SAME shape `verifyReplay` returns,
     so the banner logic is symmetric.

2. **The playback feed in `app.js`** (`Demo.step()`):
   - `const pw = this.playback ? this.playback.words[this.playback.i++] : currentPortWord()`.
     The live poke `0x810424=FF` (app.js:803) IS the file's `poke`, so no
     double-apply. PLAY ignores `?rung=` (it boots from the file's seed).
   - After `g.step(pw)`: `if (this.playback) this.playback.verifier.feed();`
   - End-of-portin: `if (this.playback && this.playback.i >= this.playback.count) this.endPlayback();`

3. **`Demo.playFrom(obj)`** -- boot a FRESH `Game` from the file's seed (mirror
   `replay.mjs:118` + W101's construction at app.js:707-711), swap it in, re-init
   the game-derived state (`prevTilt`/`prevPos`/`portList`/`seedLf`), disarm any
   armed recorder (REC/PLAY mutually exclusive), and arm the playback verifier.

4. **`Demo.endPlayback()`** -- async-finalize the verifier, build the verdict,
   mark `playback.ended` (step() then no-ops), and hand the banner state to
   `onPlaybackUpdate`. `Demo.loop()` also fires `check()` at each crossed period
   boundary so a divergence surfaces at the FIRST window, not at end-of-portin.

5. **The UI in `index.html`**:
   - A `#play` file-`<input>` (`accept=".replay,application/json"`) in `#bar`.
     On change: `arrayBuffer` -> `JSON.parse` -> `app.playFrom(obj)`.
   - `app.onPlaybackUpdate = (state) => ...` renders `#replay-banner`: a PLAYING
     line while the feed runs; a GREEN report at end-of-portin when green; a
     MISMATCH report (cumulative hash differs) or a DIVERGENT report (the first
     250-frame window, `lfA..lfB`, player hash vs recorded hash) when red.
     Never "N frames differ" (knowledge/01).

`digest.columns` is whatever the file froze; the verifier reads
`obj.digest.columns` verbatim (a trace-based replay freezes a subset, a live
REC freezes all of CLAIMED -- the player does not care).

## 6. NOTES / FORWARD

- **Live mid-play divergence:** `Demo.loop()` calls `_pollPlayback()` after each
  step batch, which hashes each newly-closed 250-frame window FRESH and surfaces
  the first divergence at the boundary (not only at end-of-portin). The async
  hash does not block the rAF; the verdict lands when the promise resolves.
- **REC/PLAY mutual exclusion:** `armRecording()` throws if playback is active;
  loading a `.replay` while REC is armed disarms REC first (the in-progress
  recording is discarded, not downloaded -- documented in the handler).
- **`?rung=` ignored by PLAY:** `playFrom` boots from the file's seed, so a rung
  in the URL is overwritten when a `.replay` is loaded. REC still honours it.
- **Per-window, not per-frame:** as with W129's headless player, the live PLAY
  surfaces the first divergent 250-frame WINDOW, not the single frame (frame-
  level needs the live trace, which a `.replay` does not carry). The banner says
  so and never prints "N frames differ" (docs/knowledge/01).
- **The visible Game IS the verify target:** no SHADOW Game is needed for
  playback -- the picture the owner watches is produced by exactly the Game
  whose state the verifier hashes. ("Verify while you play" -- a shadow running
  alongside the user's OWN run -- is a different feature and stays out of
  scope; worklog 130 section 3c/8.)
