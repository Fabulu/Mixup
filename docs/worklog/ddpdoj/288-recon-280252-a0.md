# W288: `$280252` is NOT transcribable yet, and the reason is one register

Status: RECORDED, no behaviour change. Suite 1993/1993, unchanged and green. A speculative
transcription of this body was written and **backed out** rather than shipped.

## Why this is a worklog and not a port

`$280252` is the body a long run reaches after W287, and it read as tractable: I had the whole
routine, `$280252..$280368`, and every dependency was already ported -- `$286128` (score.js),
`$242296` (aim.js), `$241D34` (vectors.js), `$28C5E4`, `$23EBA0`. I wrote it. Then the last
check failed, so it is reverted.

## THE PROBLEM: `jsr $242296` ENTERS MID-ROUTINE, AND A0 IS THE BODY'S OWN ADDRESS

    242290: bsr $24270A                  the target select -- sets A0
    242294: bcs $242264                  no target -> out
    242296: movem.w ($2,A0),D2-D3        <- THE ENTRY POINT THESE BODIES USE
    24229c: movem.w ($2,A6),D0-D1

So `$242296` reads the TARGET's position out of `($2,A0)`, and the eight callers skip the
`bsr $24270A` that would have set A0. `codexref 242296` finds exactly eight, and **all eight
are inside this same family** -- `$28029A`, `$2802DC`, `$2803B6`, `$2803F8`, `$2804D2`,
`$280514`, `$2805EE`, `$280630`, i.e. dispatch indices 8..11. So the mid-routine entry is
deliberate and shared, not an accident at one site.

Which means A0 has to hold a target when they call it. **It does not, on the reading I have:**

    27f988: lea ($27F99E,PC),A0
    27f98e: adda.w D0,A0
    27f990: movea.l (A0),A0        <- A0 becomes the DISPATCH ENTRY, i.e. the body address
    27f992: jsr (A0)

so at entry to `$280252`, A0 = `$280252`. Nothing on the not-collected path changes it before
`$28029A` (the only `lea` into A0 is `$28025A lea $817F86,A0`, and that is in the collected arm,
which returns). Taken literally, `movem.w ($2,A0),D2-D3` would read `$280254`/`$280256` --
**its own instruction stream** -- as a target position, giving D2 = `$673C`, D3 = `$7001`.

The ROM does occasionally read code as data on purpose, and this project has documented that
twice. But "the homing pickup chases coordinates made of its own opcodes" is a strong claim,
and a port that implemented it would produce plausible motion from an invented premise. That is
the one failure mode this project refuses.

## What I wrote and threw away

A full transcription: the collect arm (the `$3E7`-capped counter at `$817F86` -- already named
`POOL_A.collectP1Total` -- the `$50000` score value, `$286128`, the cue, the free), the
seed-once/re-aim-on-duty structure, the cached-pair move, the animation ring, and the draw
gate. All of it rests on `aim242296(ram, a6)` meaning something, and it does not yet.

Two things in it are worth keeping regardless, because they were read rather than guessed:

* **`($24,A6)` is the player record W287's finish family writes.** The finish hook records
  whose impact this is and the body chases that player, freeing itself if the owner's state
  word loses bit 15. The two waves confirm each other, which is the strongest evidence yet
  that W287's `($24,A0)` field is right.
* **The draw gate has TWO exemptions from the half rate, and they are different tests.** A
  quiet pool (`< $28` live) draws everything; a busy pool still draws a pickup within `$600`
  of its OWNER on the short axis. So the thing the player is about to collect keeps full
  frame rate while background debris alternates. A port keeping only the pool test would
  flicker exactly the sprite that matters most.

## How to settle it

Measure A0 at `$28029A` on the board. The oracle can do that and reasoning cannot: either the
driver differs from the reading above, or something between `$27F992` and `$28029A` sets A0,
or the family really does read its own code and the ROM's own values for D2/D3 are the
constants `$673C`/`$7001`. All three are testable and only one is true.

`tools/oracle/` already has the machinery; `w69`'s ladders carry full RAM but not registers, so
this wants a register capture at a breakpoint rather than a checkpoint.

## And the rule this wave is an instance of

Every wave this session that went well started by reading a TABLE and finding the work already
done: `$23F294` was `$23F1FA` (W275), kind 16 shared kind 1's hook (W286), eight finish hooks
were one body (W287). This one went the other way: the code read cleanly and the REGISTER
STATE did not, and no amount of reading the routine would have caught it. **A transcription is
only as sound as its entry conditions, and a mid-routine `jsr` is a signal to check them
before writing a line.**
