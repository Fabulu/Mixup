## 1. REUSABILITY MAP (Gradius to DOJ)

The three Gradius files embody the state-exact-then-synth discipline. METHOD transfers; most code does not (NES DMG/APU is unrelated to a 32-voice wavetable part). The MiSTer HDL is the strongest in-tree prior art for the chip model.

### `games/gradius/src/sound.js` -> Waves A and C (discipline transfers, code does not)

TRANSFERS directly:
- **The shadow/log/digest triple.** `state.apu[off]=v; state.apuLog.push(off,v); state.work.apuDigest = (state.work.apuDigest*31 + (off<<8) + v) & 0xFFFF`. Wave A: mailbox posts feed a mailbox-shadow + mailbox-digest compared per frame against de-duped `mailbox.tsv`. Wave C: ICS register writes feed a register-shadow + register-digest compared per frame against `ics.tsv`. The triple pattern and the count-plus-digest pair lift directly. Exact polynomial constants are the implementer's call (the DOJ tuples differ in shape: mailbox = door/payload; ics = voice/reg/half/data).
- **Flat state as one array indexed by address** (sound.js lines 36-52, 162-192). DOJ's Z80 RAM is a flat `Uint8Array`; ICS2115 per-voice state is a 32-voice struct. The principle is load-bearing for the digest to be meaningful.
- **ROM-binding pattern** (sound.js lines 136-151): module-level `let SOUND_ROM=null; bindSoundRom(tables)`, throw-on-unbound. DOJ's cue dispatch tables bind the same way: once, with a named throw.
- **Per-frame instrumentation as compared fields** (sound.js lines 420-422): `audioTicks`, `audioChannels`. DOJ needs the same: per-frame "cues posted" and "register writes" counts, compared against oracle row counts.
- **Loud-named-throw on unreachable code** (sound.js lines 312-330). Project-wide rule; sound.js is the cleanest reference.

DOES NOT TRANSFER: the NES stride-0x11 four-struct loop; the two-dialect A/B stream parser; the NMI-tick coupling mechanism. DOJ's Z80 runs independently at 8.4672 MHz.

### `games/gradius/src/audio/apu.js` -> Wave E (METHOD only, zero chip code)

TRANSFERS:
- **The narrow-claim header** (apu.js lines 9-33): register stream matches cartridge (proved per frame); this file turns the stream into samples deterministically; structural properties hold; a human said it sounds right; NO gate comparing emitted PCM against an emulator. This is EXACTLY the contract for Wave E.
- **"Model from the datasheet, not MAME; cross-check every constant a second way"** (apu.js lines 1-12, 141-168). DOJ Wave E must do the same against the W1 datasheet, classifying each MAME uncertainty per W2.
- **The structural-property gate** (apu.js lines 22-26). DOJ's list: a voice at vol 0 contributes 0; a voice at/past its end address stops; keyoff releases; the 32-voice sum does not clip at configured headroom; no NaN.
- **Determinism via exact rationals** (apu.js lines 78-83). `CPU_NUM/CPU_DEN = 19687500/11`. DOJ's ICS2115 clock (33.8688 MHz) and conversion must be integer-arithmetic the same way. NO `Math.exp` (not bit-stable across engines).
- **Throw on a register the cartridge never writes** (apu.js lines 561-573). DOJ should throw on registers C5 shows DOJ never touches.
- **Mixer-headroom discipline** (apu.js lines 170-197). Gradius precomputes the exact non-linear mixer (peak 0.6318) and sets gain for headroom. DOJ has 32 voices summing; compute the ceiling, set headroom, guarantee no clip.

DOES NOT TRANSFER: all four NES channel classes; the frame sequencer; length/sweep/envelope tables; duty cycles; the per-CPU-cycle run() loop.

### `games/gradius/src/audio/output.js` -> Wave F (the shared shim, ~60% chip-agnostic)

TRANSFERS (almost all):
- The input-granularity solution: queue per-logic-frame batches, pump to the AudioContext clock, NEVER call back into game logic. Fully chip-agnostic.
- Autoplay/unlock-on-gesture (output.js lines 143-188): start locked, do NOT create the AudioContext until `arm()` runs inside a gesture; `frame()` drops batches until then.
- Backlog ceiling / dropped-frame valve (`MAX_BACKLOG_FRAMES=15`): past it, batches still APPLY to chip state but samples are discarded. Reusable AS LONG AS the DOJ chip honors the `emit` flag.
- Underrun resync; mute-keeps-synth-running; pump-after-the-picture ordering; try/catch firewall; `stats()`.

THE REFACTOR (what makes it shared):
- **Inject the chip via a factory**: `new AudioOut(ctx, makeChip)` where `makeChip` builds a NesApu or an Ics2115.
- **Generalize the drain to N channels.** Gradius is mono end-to-end (`createBuffer(1,...)`, single-channel drain). DOJ is STEREO with per-voice pan. This is the one non-cosmetic change. If the shim does not generalize, DOJ's pan is silently flattened.
- **Add a resampler at the boundary.** The synth hands the shim `(Float32Array samples, sourceRate, channels)`. If `sourceRate === ctx.sampleRate`, schedule directly (zero-cost, Gradius today). Else resample. This is the ONE new primitive Gradius does not have.
- **Home: `shared/audio.js`** (precedent: `shared/input.js` from W109).

### In-tree prior art: the MiSTer ICS2115 HDL (stronger than prior briefs convey)

`C:\programmieren\pgm-mister\rtl\ics2115\` holds a complete SystemVerilog model: datasheet-cited (Spec 4.3), standalone-runnable sim harness (`sim/sim_ics2115_ui.cpp`), a dedicated vol/pan test ROM (`testroms/pages/ics2115_vol_pan.c`), and a remote driver (`util/ics2115_remote.py`). For Wave E's structural-property tests it can produce reference samples for the vol/pan/ulaw tables WITHOUT running the whole PGM. GPL; read-OK as reference, copy-NOT-OK into the MIT tree.

### External JS prior art: NONE

No JavaScript or browser ICS2115 emulator exists. Wave E is a fresh write against the W1 datasheet, exactly as NOTES-sound.md warns.

### Wave A: 68k cue post/queue (KEYSTONE, state-exact)

**Sizing: medium-large (1.5-2 waves).** The mechanical part is straightforward (C1's section 3 wrapper table maps every id to its addr/D0/D1/D2/type; each wrapper is a 5-line constant-set + call). The volume is ~25 `note()` sites across 13 files, plus the cue chain.

**Scope:**
1. A `sound.js` module porting the 6 entries (`$28C02A`/`$28C074`/`$28C0AE`/`$28C0E8`/`$28C0FC`/`$28C10C`), the tail `$28BFEC` (both pan subtracts `$14`/`$3C` + `$81DEB4` add + clamp), the packer `$28BB04`, and the ring enqueue `$28BAA0` (ring at `$81DD1E`, 100 slots, HEAD `$81DEAE` stride -4 wrap `$18C`, TAIL `$81DEB0` wrap `$190`).
2. The per-frame drain `$28C19A` / BIOS pump `$18ACE0`: dequeue one longword, model the `$C00004` ACK (the capture shows the board always acked within-frame, so immediate-post is the documented approximation), write to `$C10006`/`$C10008`, ring `$C00002 := $0001`.
3. The three gates `$80380A`/`$80392A`/`$803926` as RAM words the port READS exactly as the 68k does. NEVER write `$803926` from the sound side (it is dual-role: sound mute AND midboss column selector at handlers.js:3250; gameplay owns the write, sound consumes the same value).
4. Replace the ~25 `note()` placeholders (C1 section 7 maps every site to its wrapper) with real posts through the ported wrappers.
5. The debounce wrappers `$28C5E4`/`$28C714` must model the re-trigger guard (set `$81DEB6`/`$81DEB8`, early-out if already set; the drain decrements these). id `$24` fires 172x and is very sensitive to this.

**Oracle:** `mailbox.tsv` AFTER de-duping consecutive identical `OOOO=VVVV` pairs (undo the MAME tap artifact). 651 cue doors (the 6 boot/upload doors belong to Wave B/C3).

**Open items to resolve IN Wave A:**
- `$81DEB4` master-volume writer: not found by absolute-long scan. Likely set via base+disp or BIOS struct init. Must resolve before claiming state-exact (every pan byte depends on it).
- The streaming-BGM-start path (`$28CB1A`/`$28CAFC`/`$28CB60`, table `$28BBD8`, rejoiners `$28C11C`/`$28C146`, poller `$28BE76`): shares the ring/drain but has its own type/id space. mailbox shows type `$11`/`$12`/`$15` posts from this path. **Fold it in** (same enqueue, same drain).
- Indirect `jsr (A0)` dispatch (34 `lea` leads): confirm each is followed by a cue post, not a data-table read. The `$2548xx` beam-table leads (A3) are a table of wrappers; verify before porting as cues.
- The `$44` no-op sentinel: id `$44` BGM posts are silently dropped. No wrapper emits it; confirm no caller passes it inline.

**Risks:**
- `$803926` entanglement (highest): the sound gate and midboss-column selector read the same word. If Wave A models it as sound-only, the column selector and gate diverge. Resolution: READ only, never write; route the same read to the sound gate.
- The `$C00004` ACK poll is real and bidirectional. In the captured corpus the board always acked within-frame (every door fired), so the immediate-post approximation holds for the oracle. Flag for Wave C if the Z80 acks on a different timeline.
- Dead-code trap: an implementer who finds the build-B ringer `$28C226`/`$28C252` might port IT instead of the BIOS pump. It is dead. The live path is the BIOS pump `$18ACE0` only.

**Prerequisite:** silent-latch validation (extend frame.lua tap to `$C00000-$C0000D`, re-run capture). If DOJ uses `$C00005`/`$C0000D`, the oracle is incomplete and Wave A's claim is silently false. Evidence says it does not (all 657 rows from one PC, data always `$0001`), but prove it.

### Wave B: Z80 upload + driver listing (LOW RISK now)

**Sizing: small (half a wave).** The upload is trivial. The listing is a decomposition document that feeds Wave C.

**Scope:**
1. **Upload (trivial):** copy the 23416 bytes at decrypted-68k `$2C348A` into the Z80 RAM model. Assert the code region (`$0086-$5B97`) matches `z80ram.bin` byte-for-byte (23314 bytes). The 31 differing bytes all live in `$0000-$0085` (volatile runtime scratch). Done = the port produces the Z80 program and it matches.
2. **Listing:** C3 already provides the 3-layer decomposition:
   - Layer 1: register primitives (`$02AE` writeReg16, `$02A4` writeReg8hi, `$0298` readReg16, `$028E` readReg8hi, `$02C3` readReg-timer, `$0142` outToPort, `$0147` inFromPort). The COMPLETE hardware interface (7 routines).
   - Layer 2: voice engine `$376C` (32-voice per-tick update over the `$62EC` array, driven by INT `$0038` -> `$010B` -> timer-0 bit).
   - Layer 3: cue dispatch `$07F6` (NMI work: bank-select `$09B7`, read port `$8200` for command nibble, dispatch) / `$0829` (40-slot channel manager) / `$09B7` (bank-select, called 9x).
3. **Settle the bank mapping.** The NMI reads the command from port `$8200` and the payload from Z80 RAM `$6001` after a bank-select (`$09B7` with `$00F0`). The mailbox offsets (`$0006`/`$0008`) do NOT map 1:1 to Z80 RAM `$0006` (that is inside the program). C3 identified the mechanism (port `$8200` + bank-select + RAM `$6001`); Wave B nails the offset arithmetic so Wave C can reproduce cue reads.

**Risks:** minimal. The upload verbatim verdict removes the transform-hunt entirely. The bank-mapping settlement is a read-and-trace task against the disassembly, not a search.

### Wave C: Z80 driver port (THE REAL WORK)

**Sizing: large (3-5 waves).** This is the bulk of the sound port. 23 KB of compiled C, behaviorally ported against a 191,367-row oracle. Size by distinct cue behaviors and voice-state transitions, NOT by instruction count (the W83 walk-order trap, restated in CATCHUP section 3).

**Oracle:** `ics.tsv` (191,367 rows, the ordered register stream). NOT keyon.tsv (lossy, broken). Columns: `n vf lf voice reg half(sel/lo/hi) data`. The port's virtual Z80 must emit the same register-select + lo + hi sequence, voice for voice, in order.

**Scope (3 layers, in dependency order):**
1. **Register primitives** -> a virtual ICS2115 register file. A 32-voice state struct (conf, fc, oscStrt, oscEnd, oscAcc, saddr, vIncr, vStart, vEnd, volAcc, pan, vCtl, oscCtl) + a small global block (activeOsc, currentVoice, timer regs as opaque bytes). The register-write interpreter consumes the `(port, half, data)` protocol: port 1 sets regSelect; ports 2/3 write lo/hi to `voice[currentVoice][regSelect]` using the per-register authoritative half (C5's F1 table; 8b regs in one half, 16b regs in both). Small, exact. Estimated: a few hundred lines.
2. **Voice engine `$376C`** -> per-tick 32-voice update over the `$62EC` array. Advances envelopes/pitch and emits register writes. The bulk of the behavior and the bulk of `ics.tsv`.
3. **Cue dispatch `$07F6`/`$0829`/`$09B7`** -> cue-id-to-script. Depends on Wave B's bank-mapping resolution.

**Critical structural facts:**
- The main thread idles at `$114C` (`JR $`). ALL behavior is in the INT (timer, drives `$376C`) and NMI (doorbell, drives `$07F6`) handlers. A Wave C port does not need a main loop; it needs the two interrupt handlers.
- Registers are PERSISTENT across keyons (361 keyons skip loop-start; 119 program end<start). Do NOT reset a voice on keyon.
- The per-keyon invariant: the last two writes before every keyon are always `$0D=03` then `$10=00`. Hard ordering invariant.
- The 26 distinct registers DOJ touches: 19 per-voice synthesizer (`$00`-`$11`) + 7 general-purpose (`$40`/`$41`/`$42`/`$43`/`$4A`/`$4B`/`$4C`/`$4D`/`$4F`).

**Risks:**
- **Read-dependent control flow (highest).** The Z80 POLLS read registers (`$0F` IRQV 936x, `$43` timer-status ~4539x, `$40`, `$4B`). ics.tsv captures writes only. If the driver branches on a timer/IRQ read, the subsequent write sequence is data-dependent on chip state a write-only oracle cannot see. Wave C therefore needs Wave B's listing of the driver's READ/BRANCH logic, not just its write side. The B->C dependency is harder than W134 drew.
- **Timing/NMI-vs-INT ordering.** Whether the write ORDER depends on Z80 instruction timing (8.4672 MHz) or only on the frame boundary is unknown from ics.tsv alone (it carries vf/lf but not sub-frame timestamps). If only the frame boundary matters, Wave C is simpler; if sub-frame INT order matters, the timer model is load-bearing. Answerable from ics.tsv by checking whether intra-frame write ordering ever depends on a Z80 timer/NMI rather than the cue payload alone.
- **frame.lua has 3 defects** (C5 F3): the `$07` half-byte bug, 5 missing registers, 24-bit truncation. Wave C must re-derive from the datasheet + ics.tsv, NOT inherit frame.lua. Any model that "passes by reproducing keyon.tsv" has agreed with a broken snapshot.
- **Port `$8100` and `$8200` need classification.** `$8100` is written at reset and NMI-ack; `$8200` is read for the command nibble. These are PGM-specific (not ICS2115). One-line classification each: likely a Z80-side control/bank latch and the sound-command read port. W3 confirms against pgm.cpp.

### Wave D: sample data (INDEPENDENT, any time)

**Sizing: small (half a wave).** The slicing analysis is done (C4). The work is packaging + guard verification.

**Decision: ship the tight union as a single stitched `.gz` shard.** 28 disjoint byte intervals from `cave_m04401b032.u17`, merged union = 1,538,920 bytes raw / 1,156,232 gzipped (1.10 MiB). Record offsets in a sidecar index so the synth can un-stitch.

**Why this and not the alternatives:**
- Full u17 gzipped = 2.67 MiB (+99% to assets). The W119 "roughly doubles" figure.
- Contiguous slice `$000000-$35BD94` = 2.57 MiB gzip (+95%). Saves almost nothing (samples are spread across all four banks).
- **Tight union = 1.10 MiB (+41%).** 2.4x smaller than full u17. Covers 100% of the 1501 valid keyons. Needs 0 bytes from `pgm_m01s.rom`.
- **Passes the verbatim-art guard with ZERO `PUBLISH_VERBATIM` entries.** The guard (build-dist.mjs:305-328) blocks contiguous ROM runs but allows stitched non-adjacent runs. The tight union is the faithful packing (the samples themselves are non-adjacent), not a trick. `PUBLISH_VERBATIM` currently holds 6 entries; CATCHUP section 5 says a seventh is an OWNER DECISION. The stitching approach avoids burning the 7th entry on a whole ROM class.
- Fallback if sharding wants simplicity: 4 bank shards (banks 4/5/6 full, bank 7 trimmed to `$35BD94`), ~1.3-1.5 MiB gzip. But the bank-7 shard (contiguous) would trip the guard and need one `PUBLISH_VERBATIM` line.

**Risks:**
- Format assumption: "all 16-bit" is measured for stage 1 only. Later stages/BGM could use ulaw/8bit. The synth MUST honor `conf&1`/`conf&4` per voice even though stage 1 never sets them. Flag for Wave E.
- Boot-time fetch budget: 1.10 MiB sharded + deferred like BG shards does not slow first paint. Mirror the `col.shard5` "deferred, asked-for at 103 s" pattern (build-dist.mjs:189).

### Wave E: ICS2115 synth (RESEARCH)

**Sizing: research (unbounded but tractable).** The datasheet makes the synth core SMALL. The complexity is in the bit-level semantics MAME/PGMTech reverse-engineered and the volume/pan curves.

**What the datasheet licenses (the minimal faithful core):**
- 32-voice wavetable oscillator, per-voice 29-bit phase accumulator (20 integer + 9 fraction), OscFC 15-bit increment.
- Loop engine on OscStrt/OscEnd (wrap; modes from W2/MiSTer).
- THREE sample decoders: 16-bit signed linear, 8-bit linear, 8-bit u-Law. (Noise/4th format is MAME-sourced, optional.)
- Per-voice SINGLE volume ramp: VolAcc + VIncr toward VEnd, gated by VCtl, scaled by OscPan. NO LFO, NO ADSR.
- Mixer: 32 voices into a wide accumulator, saturate to 16-bit, serialize L/R, downmix to mono for PGM (L+R summed).
- Native rate: `33868800 / ((31+1)*32)` = ~33.1 kHz. Resample to AudioContext rate in Wave F.

**The bit-level questions (W1/W2 classified, Wave E implements):**
- OscConf (`$00`) format/loop bits: frame.lua says `conf&1`=ulaw, `conf&4`=8bit, else 16bit. MiSTer says bit0=u-law, bit1 selects 8-bit vs 16-bit. Settle against the primary datasheet for Wave E; irrelevant for Wave C (stored as opaque byte).
- OscCtl (`$10`): `$00`=keyon, `$0F`=keyoff (DOJ always uses these exact values). Other bits (STOP/DONE per MiSTer) may carry meaning; preserve byte-for-byte.
- VCtl (`$0D`): DOJ only ever writes `$01` or `$03`. The arm/fire trigger.
- Pan law: MiSTer measured a 16-step table (values 508/364/304/248/...); MAME guessed continuous `log2`. Prefer MiSTer's measurement.
- Timer-1 formula: MiSTer measured shift-only `(preset+1)<<(4+ctl[7:5])`; MAME used a multiply. Prefer MiSTer.
- 16-bit sample decode: MiSTer says PGM's 8-bit ROM bus repeats the addressed byte in both lanes; MAME used generic byte-pair. This is PGM-wiring-specific and load-bearing. Needs board/capture confirmation before Wave E decodes samples.
- Volume scale: logarithmic (MiSTer: 26-bit, 4-bit exponent + 8-bit mantissa). The datasheet only fixes VolAcc at 16-bit.
- Linear interpolation: the 9-bit phase fraction implies it; MiSTer confirms. Skip it and pitch-shifted samples alias/click.

**The contract (from apu.js, ratified by NOTES-sound.md):** register stream matches the capture (proved by Wave C, per frame); this file turns the stream into samples deterministically; a handful of structural properties hold; a human said it sounds right; NO gate comparing emitted PCM against MAME.

**Risks:**
- This is a research output, not "the last 10% of a port." The datasheet is public and bounds the cost; MiSTer is a usable cross-check on measured values. But the pan law, timer formula, and 16-bit decode each have a known MAME-vs-hardware divergence that must be resolved by measurement or datasheet, not by guessing.
- The `emit` flag contract is load-bearing for the backlog valve. If the synth does not honor `emit=false` (advance state, discard samples), dropping frames breaks correctness. Make it a gate.

### Wave F: shared Web Audio shim (INDEPENDENT, start now)

**Sizing: ~1 wave.** Structural risk low (method proven on Gradius). The new work: resampler + stereo.

**Scope:**

2. Add a resampler at the boundary: `(Float32Array samples, sourceRate, channels)`. If `sourceRate === ctx.sampleRate`, schedule directly. Else resample (cubic recommended from the start; linear is acceptable for a first cut). This is the ONE new primitive.

## 5. AUDIBLE-OUTPUT SCOPE DECISION

**Wave E is a research output, not "the last 10% of a port."** The audible goal is: deterministic samples built from the DATASHEET (not MAME), with hardware-fact details taken from cross-confirmed measurements (volume table, ulaw table, exponential increment, sample rate, active-osc, VMode: all cross-confirmed by MiSTer), structural properties verifiable against the register stream, and a human "sounds right."

The synth core is a 32-voice wavetable with a single volume ramp per voice. The research cost is in the bit-level semantics the datasheet omits (OscConf/OscCtl/VCtl bit layouts, pan law, timer formulas, 16-bit decode wiring, log volume scale, interpolation), all of which W1/W2 have classified and bounded.

DO NOT size Wave E by analogy to a generic Web Audio sampler synth. DO NOT let Wave E inherit frame.lua's defects. DO NOT transplant MiSTer's GPL tables into the MIT tree. DO use MiSTer's measured values as a cross-check where MAME guessed.

## 6. THE SINGLE HIGHEST-VALUE FIRST WAVE

**Wave A: the 68k cue post/queue. State-exact against de-duped `mailbox.tsv`.**

Why A first, above all others:

2. **It is state-exact (the strong gate).** The oracle is crisp: 651 cue doors, de-duped. C1 mapped every id to its wrapper addr/D0/D1/D2/type (the section 3 closed table). C2 proved the protocol (queued longword post, `$C00004` ack, constant `$0001` bell). The mechanical part is straightforward.
3. **It is independent.** Purely 68k-side. Does not wait for Wave B (upload), Wave C (driver), or Wave E (synth). Can proceed immediately.
4. **It exercises the full cue chain.** Gates, tail (pan + master vol + clamp), packer, ring, drain. If any link is wrong, the mailbox digest goes red and the implementer knows exactly where.
5. **It surfaces the entanglement risk early.** The `$803926` dual-role (sound mute vs midboss column) is the highest risk in A. Solving it first (READ only, route the same value to the gate) prevents divergence later.
