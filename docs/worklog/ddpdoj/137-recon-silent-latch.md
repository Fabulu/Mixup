# 137 -- RECON: the silent-latch validation (W135 Wave A prerequisite)

Generated by the W135 silent-latch validation. The one job: prove whether DOJ
writes sound-command bytes to the non-NMI latches `$C00005` / `$C0000D`. If it
does, `mailbox.tsv` is silently incomplete and Wave A's row-for-row claim is
false. Read-only recon; MAME was driven via `tools/oracle/pgm.py sound` over the
`stage1-deep` scenario (the same 5000-lf run that produced the existing 657-row
`mailbox.tsv`, so the numbers are directly comparable).

# 0. PREMISE (from 135-sound-architect-plan.md, section 0 item 10 + section 2)

`frame.lua` captured only `$C00002-$C00003` (the doorbell) and `$C10000-$C1FFFF`
(the payload window). PGM wires THREE soundlatch devices into `$C00000-$C0000D`
(NOTES-machine.md:226; pgm.cpp:335-340). If the 68k posts command bytes to the
other two latches, the oracle is incomplete. The plan's reassurance was "all 657
rows from one PC, data always `$0001`" -> DOJ uses the payload window only. The
job was to PROVE it by tapping the full latch range.

# 1. METHOD

Extended the sound block of `tools/oracle/frame.lua` with a fourth 68k WRITE tap
over the whole range, `PROG:install_write_tap(0xc00000, 0xc0000d, "slw", ...)`,
that attributes every write by offset + PC + data-word (histogram). write taps are
observers and coexist with the existing doorbell tap, so the `$C00002/$C00003`
rows here are a cross-check on `snd.doors`. Output: a `CENSUS sound latch_*` line
per offset written, plus `rip/sound/latchwrite.tsv` (offset, pc, count).

The byte-level map the tap was read against (pgm.cpp:335-340, cached copy at
`/tmp/claude/.../scratchpad/pgm.cpp`):

| word base | byte(s)     | handler (pgm.cpp)                       | device         |
|-----------|-------------|-----------------------------------------|----------------|
| `$C00002` | `$C00003`   | `m68k_latch1_w` + NMI pulse             | soundlatch[0]  |
| `$C00004` | `$C00005`   | `.w(soundlatch[1])`, `.r(m68k_latch_r<1>)` | soundlatch[1]  |
| `$C00006` | `$C00007`   | `v3021_device::read/write`              | V3021 RTC      |
| `$C00008` | `$C00008-9` | `z80_reset_w`                           | Z80 reset/halt |
| `$C0000A` | `$C0000A-B` | `z80_ctrl_w` (TODO no-op stub)          | Z80 bus req    |
| `$C0000C` | `$C0000D`   | `.w(soundlatch[2])`, `.r(m68k_latch_r<2>)` | soundlatch[2]  |

# 2. EVIDENCE: the census (stage1-deep, 657 doors)

```
CENSUS sound doorbells=657 z80_window_writes=336798 ics_reg_writes=191367 keyons=1620
CENSUS sound latch_writes=3477 distinct_offsets=5
CENSUS sound latch_off=C00002 total=657 pcs=[18AD78:657]                data: $0001 x657
CENSUS sound latch_off=C00006 total=156  pcs=[00B748:124 00B77C:24 ...]  data: $0000 x101, $0001 x55
CENSUS sound latch_off=C00008 total=6    pcs=[00CFAC 00D062 18B862 ...]  data: $5050 x3, $A659 x3
CENSUS sound latch_off=C0000A total=1344 pcs=[18AD20:657 18AD52:657 ...] data: $0A0A x672, $45D3 x672
CENSUS sound latch_off=C0000C total=1314 pcs=[18AD0A:657 18AD46:657]     data: $00F1 x656, $0001 x656, $00F0 x1, $0000 x1
```

The two latches the W135 plan named:

- **`$C00005` (soundlatch[1]) is NEVER written.** No word access to `$C00004`
  appears at all. soundlatch[1] is dead on this cartridge.
- **`$C0000D` (soundlatch[2]) IS written**, 1314 times (word base `$C0000C`,
  low byte -> `$C0000D`). But its data histogram has only FOUR values
  (`$00F1`, `$0001`, `$00F0`, `$0000`), against 657 doorbells. A latch carrying
  cue command bytes would have as many distinct values as there are cues; this
  one has four.

# 3. EVIDENCE: the disassembly (why `$C0000D` is handshake, not command)

The BIOS mailbox pump `$18ACE0-$18AD7E` (the single live writer of both
`$C0000C` and `$C00002`; the build-B ringer is dead code per 135 premise 2) does
this per dequeued command longword `D7`:

```
18ACE0  jsr  $18a584           ; dequeue one longword -> D0 (carry = empty)
18ACE6  bcs  $18ad7e           ; empty -> rts
18ACEA  move.l d0,d7           ; D7 = the command longword (type|pan|id|chan)
18ACEC  move.w #$f0,$81dd1a    ; (retry loop) high-nibble "pending" flag
18AD0A  move.w d0,$c0000c      ; soundlatch[2] := ($81DD18 & $0F) | $F0   [handshake]
18AD10  move.w $c00004,d0      ; poll the Z80->68K ack (soundlatch[1] read side)
18AD1E  beq  $18acec           ; spin until the Z80 acks
18AD20  move.w #$45d3,$c0000a  ; z80_ctrl bus-request ON   (MAME no-op)
18AD46  move.w d0,$c0000c      ; soundlatch[2] := ($81DD18 & $0F)         [handshake]
18AD4C  move.l d7,$c10006      ; *** THE COMMAND -> payload window (captured by mailbox.tsv)
18AD52  move.w #$0a0a,$c0000a  ; z80_ctrl bus-request OFF  (MAME no-op)
18AD5A  move.w #$1,$81dd18     ; set the sequence toggle
18AD78  move.w d0,$c00002      ; *** THE DOORBELL -> soundlatch[0] + NMI (captured)
18AD7E  rts
```

The command longword `D7` goes to `$C10006` (the payload window). soundlatch[2]
gets a byte derived from `$81DD18` (a sequence toggle: 0 on the first doorbell, 1
thereafter), NOT from `D7`. That is why the histogram is `$F0/$00` once (door 1,
seq=0) then `$F1/$01` for doors 2..657 (seq=1). The doorbell latch soundlatch[0]
always gets `$0001` (a bell, not a message); the Z80 reads the real command out
of shared RAM after the NMI.

Every other writer in the corpus confirms the same pattern: the game-code
`$28CDxx/$28CExx/$28CFxx/$28D1xx` sites all write the constant bus-request
bracket `move.w #$45d3,$c0000a` / `move.w #$0a0a,$c0000a` around their own
shared-RAM window accesses. `$C00008` (`z80_reset_w`) gets `$5050`x3 (Z80 reset)
and `$A659`x3 (Z80 halt during the program upload). `$C00006` gets RTC register
selects. None carry cue data.

# 4. VERDICT

**`mailbox.tsv` is COMPLETE as the cue-command oracle. Wave A's row-for-row
claim holds.**

- The cue command (type | pan | id | channel) is carried by the `$C10006`
  longword, which mailbox.tsv already captures as the `0006=/0008=` payload.
- The doorbell `$C00002 := $0001` is captured.
- `$C00005` (soundlatch[1]) is never written.
- `$C0000D` (soundlatch[2]) is written, but with a four-value handshake byte
  (the `$81DD18` sequence toggle), not with command bytes. The W135 conditional
  ("IF DOJ writes command bytes to the non-NMI latches") is therefore NOT
  triggered.

The plan's headline reassurance ("DOJ uses the payload window only") is correct
for command data. Its sub-claim ("Evidence says DOJ does not write `$C0000D`")
was wrong on the write-existing question but right on the only question that
matters: no command bytes go there.

# 5. THE GAP WAVE A MUST NOTE (not a blocker, but not free either)

`mailbox.tsv` is a complete record of the cue COMMAND stream, but it is NOT a
complete record of every 68k sound-latch write. Two omissions live on the
handshake side, not the command side:

1. **soundlatch[2] (`$C0000D`): 2 writes per doorbell, `$F0|seq` then `$00|seq`,
   where `seq = ($81DD18 & $0F)` (0 on door 1, 1 on every door after).** The Z80
   reads this at port `$8100`. If Wave C finds the Z80 branches on port `$8100`,
   the port must reproduce these writes (a 3-line fixed function of the doorbell
   sequence). If Wave C finds the Z80 ignores `$8100`, they are cosmetic.
2. **`z80_ctrl` (`$C0000A`): the `$45D3` / `$0A0A` bus-request bracket around
   every shared-RAM window access.** `z80_ctrl_w` is a TODO no-op stub in MAME
   (pgm.cpp:280-284), so these writes have ZERO behavioural effect on the Z80 or
   on `ics.tsv`. Safe to ignore for the port.

The `$C00008` Z80-reset and `$C00006` RTC writes are boot/calendar housekeeping
and already out of sound scope (the RTC has its own read census under
`PROBE_RTC`).
